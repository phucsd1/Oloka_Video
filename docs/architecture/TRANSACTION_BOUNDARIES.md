# Transaction Boundaries

All boundaries use repository methods through a transaction runner. They apply the SQLite PRAGMAs in `TECHNICAL_ARCHITECTURE_V1.md`; write transactions are short and use `BEGIN IMMEDIATE` when write-order certainty is required. Filesystem streaming, hashing, media inspection, and provider/network work are always outside transactions.

## Provider-intent pattern

For non-idempotent remote submission, TX-15 records an outbox/provider intent with a stable semantic request hash before or atomically around the guarded operation-reference transition. The consumer supplies that stable identifier where the provider supports idempotency. On timeout with an unknown outcome, the step enters reconciliation/waiting-provider; it does not immediately submit again. Only a proven absent operation can be resubmitted.

## Filesystem/DB ordering

SQLite cannot atomically commit with the filesystem. The selected pattern is verified staging -> atomic rename to a fresh immutable opaque key -> guarded DB commit -> reconciliation of any orphan. For purge the order is guarded eligibility -> delete/check bytes outside a transaction -> record the result. No user can resolve a key before its active DB row commits.
